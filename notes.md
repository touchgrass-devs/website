### Services - fixed 3 live-testing bugs from the phased morph (2026-07-18, third pass same day)
- **"Rectangle to circle morph looks odd" - root-caused to a border-radius mismatch, not fixed with more animation.** The card used `rounded-[32px]` while circles used `rounded-full` (9999px) - Framer's layout system has to interpolate that radius value across the same transition as a drastic width/height change (a wide card down to a small square), and animating radius and a non-uniform aspect-ratio change together is what read as "melting"/odd. Fix: circles are now a fixed `w-16 h-16` (64px, no more responsive `w-14/w-16/w-20` sizing) with the exact same `rounded-[32px]` as the card - since 64px box + 32px radius on all four corners *is* a perfect circle, both shapes now share one literal, unchanging border-radius value. Framer never animates border-radius at all anymore; only width/height/position change. The gloss reflection overlay's radius was also unconditionally set to `rounded-[32px]` (was switching between `32px`/`rounded-full` before) for the same reason.
- **"Container shrinks then grows back" - the row's own height was content-driven.** During the `'sliding'` phase all four items are briefly circle-sized (64px tall) with no card present, so the flex row's height (previously implicit, sized to its tallest child) collapsed to 64px and then jumped back to ~500px once the new card grew in - a visible layout lurch. Fixed by moving the fixed height classes (`h-[460px] sm:h-[440px] md:h-[500px]`) onto the *outer* carousel wrapper (not just the card element), with `items-center` to vertically center whatever's inside. The stage now always reserves the card's full height regardless of phase, so nothing above/below it in the page shifts during a transition.
- **"Should jump like boink, not slide" - added a distinct hop to the one item making the long end-to-end move.** Every other item in a rotation only shifts one slot over (a normal reflow), but the item going from last-to-first (`next`) or first-to-last (`prev`) travels the whole row - that's the one that reads as a "jump." Added `jumpingIdRef`, set right before the reorder fires (via a `jumperFromOrder` accessor passed into `advance()`, e.g. `(order) => order[3]` for `next`), and during the `'sliding'` phase that one item gets an extra `animate={{ y: [0, -22, 0] }}` hop layered on top of its normal horizontal layout slide (via Framer's per-property `transition={{ layout: {...}, y: {...} }}` syntax, not a second competing `transition` prop). The shared layout spring was also tuned snappier (`stiffness 340, damping 26` vs the prior `260/30`) so the horizontal move itself has a bit more pop rather than reading as a flat linear slide.
- **Not yet live-verified** - same standing sandbox caveat; worth checking that the 64px-fixed circle size (down from the previous responsive 56-80px range) still looks right at every breakpoint, and that the hop height/timing (22px over 420ms) feels like a "boink" rather than too subtle or too much.

New `useInertialSpin()` hook: a rotation `angle` motion value accumulates every frame via `useAnimationFrame` (`angle += direction * speed * deltaSeconds`), while `speed` is a separate motion value that gets spring-animated (`animate(speed, target, { type:'spring', stiffness:120, damping:18 })`) between a slow `baseSpeed` and a much faster `fastSpeed` whenever the carousel's `phase` state moves in or out of `'idle'`. Because the angle keeps accumulating continuously regardless of what `speed` is doing, there's never a reset or discontinuity - just a smooth spring ramp up in speed during `next`/`prev` (both `'shrinking'` and `'sliding'` count as "switching"), and an equally smooth spring ease back down to idle speed once `phase` returns to `'idle'`. The two corner shapes spin opposite directions (`direction: 1` / `-1`) at slightly different base/fast speeds so they don't read as a mirrored pair. `prefers-reduced-motion` zeroes `speed` outright (no spin at all, static), consistent with every other animated element on this page.

Worth confirming in a real browser that: the larger/longer-armed shapes still look premium (not busy) at the quadrant crop, and that the speed-up is actually perceptible during the ~680ms switch window (shrink 260ms + slide 420ms) without looking like a jarring flick - the spring constants (`stiffness 120 / damping 18`) are a first-pass tuned to *mostly* reach the faster speed by the time the switch completes, then ease back down after.
